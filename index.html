Pattern 00 · before you build

Set the platform up once, then reuse it everywhere

Every project here runs against the same Google Cloud project, the same auth, and the same model family. Get this right once and the six patterns become variations on a theme rather than six setups.

Project & auth bootstrap

  1. Create or pick a project and enable the platform API: gcloud services enable aiplatform.googleapis.com
  2. Authenticate with Application Default Credentials: gcloud auth application-default login
  3. Export the two env vars every SDK reads: GOOGLE_CLOUD_PROJECT and GOOGLE_CLOUD_LOCATION (e.g. us-central1)
  4. Point the GenAI SDK at the platform backend: GOOGLE_GENAI_USE_VERTEXAI=true
  5. Install the two libraries the projects share: pip install google-genai google-cloud-aiplatform
  6. For data work add google-cloud-bigquery and google-cloud-storage
Naming note. Google renamed Vertex AI to the Gemini Enterprise Agent Platform in April 2026, but the SDKs, the aiplatform API, and most docs still say "Vertex AI." Treat the two names as the same thing throughout this manual.

PATTERN 01

Hybrid RAG with reranking & citations

Answer questions from internal docs by combining keyword precision with semantic recall, sharpening the result set with a reranker, and forcing the model to cite the source of every claim.

The idea

Pure semantic search misses exact tokens — product codes, error strings, acronyms. Pure keyword search misses meaning — "car repair" never matches "automobile maintenance." Hybrid search runs both: a dense vector for meaning and a sparse vector for keywords, then fuses the two ranked lists with Reciprocal Rank Fusion (an alpha dial trades keyword vs. semantic weight).

Fusion gets you a good top-50. A cross-encoder reranker then reads the query against each candidate and reorders for true relevance — this is the single biggest quality lever in most RAG systems. Finally, you keep document IDs flowing through the whole pipeline so the answer can carry inline citations back to the exact chunk, which is what makes the system trustworthy.

Build path
  1. Chunk thoughtfully. 300–600 token chunks with ~15% overlap; store doc_id, title, url, and character offsets as metadata.
  2. Make both vectors. Dense from text-embedding-005; sparse from a TF-IDF/SPLADE-style encoder. Write a JSONL of datapoints carrying embedding + sparse_embedding.
  3. Stand up the index. Create a Vector Search index + endpoint, deploy, and upsert. (Vector Search 2.0 Collections store vectors, metadata, and content together.)
  4. Retrieve hybrid. Embed the query both ways, query the index, fuse the two rankings with RRF and a tunable alpha.
  5. Rerank. Send query + candidate texts to the Ranking API; keep the top-k by model score.
  6. Generate with citations. Number the surviving chunks, instruct Gemini to cite [n] after every claim, then resolve [n] → title/url for the UI.
Reference code · retrieve → rerank → cite
rag/pipeline.pypython
# hybrid retrieve, rerank with the Ranking API, then ground Gemini with citations
from google import genai
from google.genai import types
from google.cloud import discoveryengine_v1 as de

client = genai.Client(vertexai=True, location="us-central1")

def answer(query, chunks):           # chunks = top-50 from hybrid search
    ranked = rerank(query, chunks)[:8]
    context = "\n\n".join(f"[{i+1}] {c.text}" for i, c in enumerate(ranked))
    prompt = ("Answer using ONLY the context. After every claim cite [n]. "
              f"If unsupported, say so.\n\nCONTEXT:\n{context}\n\nQ: {query}")
    resp = client.models.generate_content(
        model="gemini-2.5-pro", contents=prompt,
        config=types.GenerateContentConfig(temperature=0.1))
    sources = [{"n": i+1, "title": c.title, "url": c.url}
               for i, c in enumerate(ranked)]
    return resp.text, sources    # UI renders [n] → clickable source

def rerank(query, chunks):
    rank = de.RankServiceClient()
    records = [de.RankingRecord(id=str(i), content=c.text)
               for i, c in enumerate(chunks)]
    res = rank.rank(request=de.RankRequest(
        ranking_config=RANK_CFG, model="semantic-ranker-fast-004",
        query=query, records=records, top_n=8))
    return [chunks[int(r.id)] for r in res.records]
Project brief
Hybrid search over internal docs
  • Ingests a folder of internal docs into a hybrid Vector Search index
  • Retrieves with both vectors and exposes the RRF alpha dial
  • Reranks candidates through the Ranking API
  • Returns answers with inline [n] citations resolving to source title + URL
  • Refuses to answer when the context doesn't support a claim

PATTERN 02

Agent orchestration: tools, memory, human-in-the-loop

Give a model tools it can call, memory that survives the session, and an approval gate a human must clear before anything irreversible runs.

The idea

An agent is a loop: the model reads state, decides whether to answer or call a tool, you run the tool, feed the result back, repeat. Three things turn that loop into a system. Tools are just typed Python functions the model can call. Memory separates short-term session state from long-term facts that persist across conversations. Human-in-the-loop pauses the loop before a sensitive action and waits for a yes.

On GCP the Agent Development Kit (ADK) is the code-first surface for this — model-agnostic, Python/Go/Java/TS, with a graph framework for routing a supervisor to specialized sub-agents. Memory Bank holds long-term memory, Sessions hold conversation state, and Agent Engine is the managed runtime that handles autoscaling and long-running execution.

Build path
  1. Write tools as functions. Type hints + docstrings become the model's tool schema — the docstring is the prompt the model reads to decide when to call it.
  2. Define the agent. An LlmAgent with an instruction, a model, and its tool list.
  3. Add session + memory. Sessions carry the running conversation; Memory Bank stores durable facts you generate and fetch by user.
  4. Wrap sensitive tools in a gate. Mark tools like "issue refund" or "send email" as requiring confirmation; the runtime interrupts and waits for approval.
  5. Compose sub-agents. A supervisor routes to specialists (e.g. a billing agent, a docs agent) over the ADK graph.
  6. Deploy to Agent Engine. Hand the agent to the managed runtime for autoscaling, sessions, and long-running state.
Reference code · tool + HITL gate
agent/app.pypython
# ADK agent: a safe tool, a gated sensitive tool, plus memory
from google.adk.agents import LlmAgent
from google.adk.tools import ToolContext

def lookup_order(order_id: str) -> dict:
    """Read-only: fetch an order's status and total."""
    return db.get_order(order_id)

def issue_refund(order_id: str, amount: float, tool_context: ToolContext) -> dict:
    """Irreversible: refund money. Requires human approval first."""
    if not tool_context.state.get("approved"):
        return {"status": "PENDING_APPROVAL",        # pause the loop
                "confirm": f"Refund ${amount} on {order_id}?"}
    return payments.refund(order_id, amount)

support = LlmAgent(
    name="support", model="gemini-2.5-flash",
    instruction="Help customers. Always confirm before issuing refunds.",
    tools=[lookup_order, issue_refund])      # memory + sessions attach via Agent Engine

Orchestration with tools, memory & HITL

  • Three+ tools, one of which is irreversible and gated
  • Session state for the live conversation
  • Long-term memory that survives across conversations
  • A blocking approval step a human must clear before the gated tool runs

PATTERN 03

LLMOps: a semantic cache that halves the bill

Most production traffic is near-duplicate questions. Embed each incoming prompt, look for a semantically similar one you've already answered, and serve the stored answer instead of paying for another generation.

The idea

An exact-match cache almost never hits — "what's your refund policy?" and "how do I get a refund?" are different strings but the same question. A semantic cache stores the embedding of every answered prompt. A new request is embedded and matched by cosine similarity; above a threshold it's a hit and you return the cached response for the price of one cheap embedding call.

The two dials that matter: the similarity threshold (too low and you serve wrong answers; too high and you never hit) and the TTL (so stale answers expire). Pair this with Gemini's native context caching for the orthogonal win — caching a large shared prefix (a long system prompt or document) so you stop re-paying input tokens on every call.

Build path
  1. Wrap the model client. A thin proxy that owns the cache lookup so callers don't change.
  2. Embed and search. On each request, embed the prompt and run a cosine top-1 against the cache store.
  3. Set the threshold honestly. Calibrate τ on real traffic — measure wrong-hit rate, not just hit-rate.
  4. Store on miss. Save {vector, prompt, response, ttl}; let Redis expire stale entries.
  5. Add native context caching. For long shared prefixes, register a cached content handle and reference it to cut input-token cost.
  6. Instrument the win. Emit hit-rate and "tokens avoided × price" so you can prove the bill dropped.
Reference code · the cache check
llmops/semantic_cache.pypython
# serve from cache when a semantically similar prompt was already answered
def complete(prompt, threshold=0.92):
    vec = embed(prompt)                         # text-embedding-005
    hit, score = cache.nearest(vec)            # cosine top-1 from Redis
    if hit and score >= threshold:
        metrics.record("hit", saved_tokens=hit.tokens)
        return hit.response, {"cached": True, "score": score}

    answer = client.models.generate_content(       # MISS → pay once
        model="gemini-2.5-flash", contents=prompt).text
    cache.put(vec, prompt, answer, ttl=86400)     # 24h TTL
    metrics.record("miss")
    return answer, {"cached": False}
Project brief
Semantic cache that cuts the API bill in half
  • Drop-in proxy in front of Gemini — callers unchanged
  • Embedding-based lookup with a tunable similarity threshold
  • Vector store with TTL eviction (Redis or pgvector)
  • A metrics endpoint reporting hit-rate, tokens avoided, and $ saved
  • A replay script that proves ≥ 50% savings on a real prompt log

PATTERN 04

Evals from real production logs

Stop hand-writing test cases. Mine your own traffic — cluster real queries, sample a representative set, auto-generate grading rubrics, and turn it into a versioned eval suite you can run on every change.

The idea

Synthetic test sets test the cases you already imagined. The interesting failures live in production. The move: pull request/response logs, embed and cluster them so you cover the real distribution instead of over-sampling the common path, take a stratified sample, then use a strong model as a generator to write each case's expected answer or grading rubric. A human reviews a slice for sign-off, and the result is a versioned dataset.

Then you grade with the Vertex AI Gen AI Evaluation Service: computational metrics (exact-match, ROUGE) where there's a reference, and model-based autorater metrics (an LLM-as-judge scoring helpfulness, groundedness, safety) where there isn't. Run it in CI so quality is a number that moves, not a vibe.

  2. Embed & cluster. Vectorize queries, cluster (k-means / HDBSCAN) to discover intents and their frequencies.
  3. Stratified sample. Pull N per cluster plus outliers so the suite mirrors production and includes the long tail.
  4. Generate cases. For each sampled query, have Gemini draft a reference answer and a rubric (groundedness, completeness, tone).
  5. Human review. Approve/edit a slice; mark each case verified; version the dataset in GCS.
  6. Score & gate. Run the Evaluation Service on each candidate model/prompt; fail CI if a metric regresses.

# turn one real logged query into a graded eval case
RUBRIC = """From this real user query + the answer we served, produce JSON:
{"input": str, "reference": str, "rubric": [str], "tags": [str]}
The reference is the ideal grounded answer; rubric = pass/fail checks."""

def make_case(logged_query, served_answer):
    resp = client.models.generate_content(
        model="gemini-3.1-pro",
        contents=f"{RUBRIC}\n\nQUERY: {logged_query}\nSERVED: {served_answer}",
        config=types.GenerateContentConfig(
            response_mime_type="application/json", temperature=0.2))
    return json.loads(resp.text)        # → append to versioned eval set

  • Clusters queries and samples a representative + edge-case set
  • Generates a reference answer and rubric per case with Gemini
  • Emits a versioned eval dataset + a human-review queue
  • Runs the Evaluation Service and prints a scored report

PATTERN 05

LoRA fine-tuning: base model → benchmark

When prompting can't get the model to match your domain's format, terminology, or style, train LoRA adapters on a few hundred good examples and prove the win against the base model on a held-out set.

The idea

Vertex's supervised fine-tuning doesn't update the whole model — it uses LoRA (PEFT): the base weights freeze, and small low-rank adapter matrices are trained and injected into the transformer layers. You save megabytes of adapters, not a fresh copy of the model, and a single base can serve many adapters. The one dial that matters most is adapter_size (the LoRA rank, 1–8): bigger learns more but risks overfitting.

The pipeline is the point: curate a clean JSONL dataset, launch an SFT job pinned to a base like gemini-2.5-flash, deploy the resulting adapter to an endpoint, and then — critically — benchmark base vs. tuned on data the model never saw. If you want downloadable weights, run LoRA on open-weight gemma-4 via a custom training job instead.

Build path
  1. Curate, don't dump. A few hundred high-quality, consistent examples beat thousands of noisy ones. Hold out a real validation slice.
  2. Format JSONL. One example per line as input/output (or messages); upload train + val to GCS.
  3. Launch SFT. Pin source_model, set adapter_size and epochs; the job trains and registers the adapter.
  4. Deploy. The tuned model becomes an endpoint resource you call exactly like the base.
  5. Benchmark honestly. Run base and tuned over the held-out set with the same metrics; report the delta.
  6. Iterate on data. Most gains come from fixing the dataset, not cranking the rank.
Reference code · launch SFT & compare
tuning/run_lora.pypython
# supervised LoRA tuning on Vertex, then benchmark vs the base
from vertexai.tuning import sft

job = sft.train(
    source_model="gemini-2.5-flash",
    train_dataset="gs://my-bucket/train.jsonl",
    validation_dataset="gs://my-bucket/val.jsonl",
    epochs=3, adapter_size=4,          # LoRA rank
    tuned_model_display_name="support-summarizer-v1")
job.refresh()                            # poll until done

tuned = job.tuned_model_endpoint_name        # deployed automatically
for model in ["gemini-2.5-flash", tuned]:    # base vs tuned, same metrics
    score = evaluate(model, held_out)
    print(model, score)                    # report the lift

PATTERN 06

Guarded text-to-SQL

Let users ask questions in English and get SQL back — but never let a generated query mutate or destroy data. Validate the query's structure, not just its words, before a single byte runs.

The idea

A model that writes SQL will, sooner or later, write DELETE or DROP — through a clever prompt, a misunderstanding, or an injected instruction. You cannot prompt your way to safety; you need defense in depth. Generate SQL grounded in the real schema and constrained to SELECT. Then parse the generated SQL into an AST and reject anything that isn't a read: no DML/DDL, no multiple statements, only allow-listed tables, a mandatory LIMIT.

Even a valid-looking SELECT runs under two more guards: a BigQuery dry-run that validates and estimates cost without executing, and a read-only service account that physically lacks write permission. Generation is a suggestion; the parser and the IAM role are the law.

Build path
  1. Ground the prompt in schema. Pass table/column definitions; instruct read-only SELECT and a forced LIMIT.
  2. Parse to an AST. Use sqlglot — string matching for "DROP" is trivially bypassed; an AST is not.
  3. Reject by structure. Block anything that isn't a single SELECT: no INSERT/UPDATE/DELETE/DROP/ALTER/TRUNCATE/MERGE, no stacked statements.
  4. Enforce policy. Allow-list tables and columns; require a LIMIT; cap scanned bytes.
  5. Dry-run. Ask BigQuery to validate and estimate before executing for real.
  6. Execute least-privilege. Run under a service account with read-only access so a bug can't become a breach.
Reference code · the structural gate
guardrails/validate_sql.pypython
# the query is guilty until the AST proves it's a harmless read
import sqlglot
from sqlglot import exp

BLOCKED = (exp.Insert, exp.Update, exp.Delete, exp.Drop,
           exp.Alter, exp.Create, exp.Command)   # TRUNCATE, etc.

def assert_safe(sql, allowed_tables):
    trees = sqlglot.parse(sql, read="bigquery")
    if len(trees) != 1:
        raise Unsafe("multiple statements")     # no stacking
    tree = trees[0]
    if not isinstance(tree, exp.Select):
        raise Unsafe("only SELECT is permitted")
    if any(tree.find(b) for b in BLOCKED):
        raise Unsafe("destructive operation")
    for t in tree.find_all(exp.Table):
        if t.name not in allowed_tables:
            raise Unsafe(f"table not allow-listed: {t.name}")
    if not tree.find(exp.Limit):
        sql += " LIMIT 1000"                  # force a ceiling
    return sql                              # then: BQ dry-run, then read-only execute
Project brief
Text-to-SQL that blocks destructive queries
  • Generates schema-grounded SQL from a natural-language question
  • Parses to an AST and rejects all non-SELECT operations
  • Enforces a table/column allow-list and a mandatory LIMIT
  • Dry-runs against BigQuery before any real execution
  • Executes under read-only credentials and returns a safety report
  • Ships with an attack-suite of injection attempts that all get blocked
